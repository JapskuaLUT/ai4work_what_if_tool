# Database Setup & Migrations

This document explains how database migrations work in this project and how to manage them.

## 🚀 Quick Start (Fresh Setup)

When you clone this repository and start the project for the first time:

```bash
# Start all services with Docker Compose
docker-compose up -d
```

**That's it!** Database migrations are applied automatically. ✅

The backend service will:
1. Wait for PostgreSQL to be ready
2. Automatically apply all pending migrations
3. Start the server

## 📋 How It Works

### Automatic Migration on Startup

The project is configured to run database migrations automatically whenever the backend container starts.

**Configuration:**
- [docker-compose.yml](../docker-compose.yml) - Backend service uses `command: bun run dev:migrate`
- [scripts/migrate-and-start.sh](scripts/migrate-and-start.sh) - Startup script that runs migrations
- Backend service has `depends_on` PostgreSQL with health check

**Startup Flow:**
```
1. Docker Compose starts PostgreSQL container
2. PostgreSQL health check runs (pg_isready)
3. Backend container starts after PostgreSQL is healthy
4. migrate-and-start.sh script executes:
   ├─ Wait for PostgreSQL to be fully ready
   ├─ Run: bunx drizzle-kit push:pg
   ├─ Apply any pending migrations
   └─ Start backend server with: bun run --watch src/index.ts
```

### Migration Files

Migration SQL files are stored in `/backend/drizzle/`:

```
drizzle/
├── 0000_same_namor.sql        # Base tables (simulation_sets, scenarios, etc.)
├── 0001_sticky_lester.sql     # Educational tables (educational_simulations, adjustment_scenarios)
└── meta/                       # Migration metadata
```

These files are generated by Drizzle Kit and committed to git.

## 🛠️ Manual Migration Commands

While migrations run automatically, you can also run them manually:

### Push Migrations (Recommended)

```bash
# Inside backend directory
cd backend

# Apply all pending migrations
bun run db:push
```

This compares your schema ([src/db/schema.ts](src/db/schema.ts)) with the database and applies any differences.

### Generate New Migrations

When you modify `src/db/schema.ts`:

```bash
# Generate migration SQL files
bun run db:generate

# Apply the generated migrations
bun run db:push
```

### Open Database Studio

Drizzle Studio provides a GUI for viewing/editing database data:

```bash
bun run db:studio
```

Opens at: http://localhost:4983

## 📝 Schema Changes Workflow

### 1. Modify Schema

Edit [src/db/schema.ts](src/db/schema.ts):

```typescript
export const my_new_table = pgTable("my_new_table", {
    id: serial("id").primaryKey(),
    name: text("name").notNull(),
    created_at: timestamp("created_at").defaultNow()
});
```

### 2. Generate Migration

```bash
cd backend
bun run db:generate
```

This creates a new SQL file in `drizzle/` like `0002_amazing_spiderman.sql`

### 3. Review Migration

Check the generated SQL to ensure it's correct:

```bash
cat drizzle/0002_*.sql
```

### 4. Apply Migration

**Option A: Let Docker do it automatically**
```bash
docker-compose restart backend
```

**Option B: Apply manually**
```bash
bun run db:push
```

### 5. Commit Changes

```bash
git add src/db/schema.ts drizzle/
git commit -m "feat(db): add my_new_table"
```

## 🐛 Troubleshooting

### "relation does not exist" Error

**Cause:** Database schema is out of sync with code.

**Solution:**
```bash
# Stop all services
docker-compose down

# Start again (migrations will run automatically)
docker-compose up -d

# Check backend logs
docker-compose logs backend
```

You should see:
```
🔄 Starting backend with automatic migrations...
⏳ Waiting for PostgreSQL to be ready...
✅ PostgreSQL is ready!
🗄️  Applying database migrations...
✅ Database migrations applied successfully!
🚀 Starting backend server...
```

### Migrations Not Running

**Check backend logs:**
```bash
docker-compose logs backend
```

**Verify PostgreSQL is running:**
```bash
docker-compose ps postgres
```

**Manually trigger migrations:**
```bash
docker-compose exec backend bun run db:push
```

### Database Connection Issues

**Check DATABASE_URL:**
```bash
docker-compose exec backend env | grep DATABASE_URL
```

Should be: `postgres://whatifuser:whatifpassword@postgres:5432/whatifdatabase`

**Test connection:**
```bash
docker-compose exec backend bunx drizzle-kit push:pg --config=drizzle.config.ts
```

### Fresh Database Reset

⚠️ **Warning:** This deletes all data!

```bash
# Stop services
docker-compose down

# Remove database volume
rm -rf postgres_whatif_data/

# Start fresh (migrations will run automatically)
docker-compose up -d
```

## 🔧 Configuration Files

### [drizzle.config.ts](drizzle.config.ts)

Drizzle Kit configuration:

```typescript
export default {
    schema: "./src/db/schema.ts",           // Schema definition
    out: "./drizzle",                       // Migration output directory
    driver: "pg",                           // PostgreSQL driver
    dbCredentials: {
        connectionString: process.env.DATABASE_URL || "..."
    }
};
```

### [scripts/migrate-and-start.sh](scripts/migrate-and-start.sh)

Startup script with automatic migrations:

```bash
#!/bin/bash
set -e

# Wait for PostgreSQL to be ready
# Apply migrations: bunx drizzle-kit push:pg
# Start server: bun run --watch src/index.ts
```

### [docker-compose.yml](../docker-compose.yml)

Backend service configuration:

```yaml
backend:
    command: bun run dev:migrate    # Uses startup script
    depends_on:
        postgres:
            condition: service_healthy    # Wait for DB health check
    environment:
        - DATABASE_URL=postgres://...
```

## ✅ Best Practices

1. **Always generate migrations for schema changes**
   - Don't manually edit migration files
   - Use `bun run db:generate` to create migrations

2. **Review generated SQL before applying**
   - Check migration files in `drizzle/`
   - Ensure they match your intended changes

3. **Commit migrations to git**
   - Migration files should be version controlled
   - This ensures team members get the same schema

4. **Test migrations locally first**
   - Apply migrations in development
   - Verify everything works
   - Then deploy to production

5. **Use automatic migrations in Docker**
   - Let the startup script handle migrations
   - Prevents "relation does not exist" errors
   - Ensures fresh setups work immediately
